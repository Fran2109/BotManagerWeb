# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Web/Capacitor port of the React Native app in `../BotManager`: a client for **Automation Anywhere Community Edition** Control Rooms that lists bots, deploys them to a user's device, and shows in-progress activities, execution history and device status. Stack: React 19 + TypeScript + Vite + Tailwind CSS v4 (`@tailwindcss/vite`, no config file) + Capacitor 8 (Android only).

## Commands

```bash
npm run dev          # Vite dev server (browser); Control Room calls go through the Vite proxy
npm run typecheck    # tsc --noEmit
npm run build        # typecheck + build to dist/
npx cap sync android # copy dist/ into the Android project (run after every build)
npx cap run android  # install on a device/emulator (needs JDK + Android SDK)
npx cap open android # open in Android Studio
npm run android      # build + sync + run
```

There are no tests.

## Configuration

`.env` (git-ignored, see `.env.example`) uses the `VITE_` prefix. `src/env.ts` re-exports the values under the old react-native-dotenv names, and `vite.config.ts`/`tsconfig.json` alias `@env` to it, so code ported from the RN app keeps `import { X } from '@env'`. Values are inlined into the bundle at build time.

## Architecture

- **Networking / CORS.** The Control Rooms send no CORS headers. In the browser dev server, `env.ts` points `AA_COMMUNITY_URL`/`AA_COMMUNITY2_URL` at `${origin}/aa1/` and `/aa2/`, which `vite.config.ts` proxies to the real hosts. On Android, `CapacitorHttp` (enabled in `capacitor.config.json`) patches XHR/fetch to run natively, so the real URLs are used. A plain `vite preview`/static deploy in a browser has neither and will fail on CORS.
- **`src/Functions.ts`** — the whole API layer (axios, AA `v2`/`v3` REST). Mostly unchanged from the RN app, with three fixes:
  - a request interceptor sets `baseURL` per request from `_userEmail` (most calls use relative URLs, and the global `axios.defaults.baseURL` is overwritten whenever another user's token is fetched);
  - `getToken` shares an in-flight login per user (a new login invalidates the user's previous token);
  - the 401/403 retry interceptor reuses a token already refreshed by another request instead of logging in again.
  Every request must pass `_userEmail` in its config (typed in `src/types/axios.d.ts`). Users map to Control Rooms in `getBaseURLByUsername`; adding a user also means `.env`, `src/env.ts`, `src/vite-env.d.ts` and `src/constants/users.ts`.
- **`src/hooks/`, `src/utils/`, `src/constants/`, `src/types/`** — copied from the RN app; screen-level state hooks. `useBotExecution.executeBot` is the deploy pipeline (token → device `CONNECTED` → `checkBotExists` → userId → `deployBot`). `utils/botVariables.ts` holds the pure helpers for `BotVariablesModal` (DATETIME is sent as `YYYY-MM-DDTHH:mm:00-03:00[America/Argentina/Buenos_Aires]`).
- **Navigation** — mirrors the AA Control Room: routes and labels live in `navigation/drawerContext.ts` (`ROUTE_META`: Automation › Bots, Activity › In progress / Historical, Manage › Devices); keep new screens in those groups and use Control Room wording. `navigation/DrawerNavigator.tsx` replaces react-navigation: a state-driven drawer (styled as the Control Room's nav pane) that mounts one screen at a time, so leaving a screen unmounts it. `useDrawer().navigate(route)` switches screens from anywhere (e.g. "View in progress" after launching). The header shows "Group / Page". The context lives apart from the navigator to avoid an import cycle with `Header`.
- **Phone sizes and orientation** — the app must work from 320 px wide and in landscape. Use the `land:` variant (landscape under 520 px tall, defined in `index.css`) to compact vertical chrome; wrap edge-touching bars/screens in `safe-x` (left/right insets) besides `safe-top`/`safe-bottom` (all read `--inset-*`, which combine `env()` with Capacitor's injected vars). Text sizes in `rem`, not `px`. Where a row of fixed 44 px controls may not fit, use a container query in `rem` (see `Paginator`) so it also adapts to large system text. Center dialogs are height-capped and scroll inside. Results of the size/orientation audit are in `docs/auditoria-ux.md`.
- **Statistics** — Activity › Statistics (`screens/StatisticsScreen.tsx`) and the last-run line under each bot come from `hooks/useRunStats.ts`: it pages `getExecutionHistory` with `since` for every account (CE has no Bot Insight), groups runs by bot **name** (the same bot has a different file id in each account) and caches the result for a minute so both screens share one fetch. Status labels, success/failure rules and date/duration formatting live in `lib/runStatus.ts` (also used by `HistoryCard`).
- **Favorites and recents** — `lib/launchHistory.ts` keeps them in localStorage (`useSyncExternalStore` hooks). The star in the Run bot now sheet toggles a favorite; every successful launch is recorded with its account, options and inputs. At the root of Bots, Favorites and Recent panels appear above the list; a recent opens `RepeatLaunchModal` (Run again = `handleUserSelection` with the saved options, Bot inputs prefilled via `initialInputs`; Change options = the normal sheet with `initialOptions`).
- **Schedules (phone-side)** — Community Edition rejects Control Room schedules (`POST v2/schedule/automations` → 403 "You no longer have permission to schedule a bot"; verified), so on Android the phone launches bots itself. The "Schedule" button in the Run bot now sheet opens `ScheduleModal` (account, once/every day/some days, time, options); if the bot has inputs, Bot inputs opens with "Save schedule". `lib/schedules.ts` resolves the bot's fileId and the userId in that account at creation and calls the native plugin (`lib/nativePlugin.ts`, the single `registerPlugin('RunTracker')`). Natively, `ScheduleManager` stores schedules in SharedPreferences and sets `setExactAndAllowWhileIdle` alarms (inexact without the "Alarms & reminders" permission; the UI warns and links to the setting); `ScheduleReceiver` hands due runs to `RunTrackerService` (`ACTION_RUN_SCHEDULE`: login → device must be CONNECTED → `v3/automations/deploy`, retries 10 min offline, optional tracking) and re-arms on boot/update/permission change. Runs due while the phone was off, or delivered >15 min late, are reported as missed, never launched late. Plugin `load()` re-arms everything (force-stop clears alarms). The password is stored natively but never returned to the WebView. Activity › Scheduled lists, pauses and deletes them. Verified on the Android 15 emulator against an offline account (so nothing was deployed).
- **PC disconnection alerts (Android)** — Devices has a per-account "Alert me if it disconnects" switch (`lib/deviceAlerts.ts` → plugin `setDeviceAlert` / `getDeviceAlerts` / `checkDevicesNow`). Natively, `DeviceWatcher` keeps watched accounts in SharedPreferences (`device-watch`, password/token never returned to the WebView) and sets an inexact `setAndAllowWhileIdle` alarm (~15 min, Android may defer it to ~26 min) handled by `ScheduleReceiver` with `goAsync` (no foreground service). Each check calls `v2/devices/list` (re-login on 401/403). CONNECTED → not connected sets `pendingDown` and a 2-minute confirm alarm; only a second non-connected result alerts (channel `device-alerts`), so brief drops don't. DISCONNECTED → CONNECTED notifies "back online" (same notification id per account). Network/Control Room errors never change the state; the first check after enabling is a silent baseline. Re-armed on boot and in plugin `load()`. `ScheduleReceiver` is not exported, so tests can't `am broadcast` to it: edit `shared_prefs/device-watch.xml` with `run-as` (app stopped), call `checkDevicesNow()` over CDP, then let the real confirm alarm fire with the app closed.
- **Run notifications** — "Notify me while it runs" in the Run bot now sheet (remembered in localStorage) makes `BotManagerScreen` call `trackRun()` (`lib/runTracker.ts`) after a successful deploy. **On Android** it hands the run to `RunTrackerService` (`android/app/src/main/java/com/botmanager/web/`), a `dataSync` foreground service bridged by the app-local `RunTrackerPlugin` (registered in `MainActivity`). The service polls `v3/activity/list` by deploymentId every 10 s with its own HTTP client, re-logs in on 401/403 (it receives the base URL, token and credentials), keeps a partial wake lock while runs exist, and its own ongoing notification is the progress notification (progress bar for one run, a list for several); results go to channel `bot-finished`, taps open In progress/Historical via the `openRoute` event / `getLaunchRoute()`. Runs persist in SharedPreferences and resume when the app opens (e.g. after a force-stop). Failure handling is the same in Java and JS: offline never ends tracking (network callback / `online` event re-check at once), rejected credentials stop after 3 tries, 5xx backs off for up to 30 min. **On the web** the JS tracker in `runTracker.ts` does the polling and uses `@capacitor/local-notifications`. Notification small icon: `res/drawable/ic_stat_bot.xml`.
- **End-to-end testing** — build with `VITE_E2E=1 npm run build` to expose `window.__e2e.trackRun` (stripped from normal builds) and follow an existing deploymentId without launching a bot. The run tracker was verified on an Android 15 emulator (AVD `botmanager-test`; start it with `emulator -avd botmanager-test`), driving the WebView over DevTools (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`) and toggling `cmd connectivity airplane-mode`. Don't ship an E2E build.
- **Polling** — screens poll through `hooks/usePolling.ts`, which pauses while the app is hidden and refreshes on return; don't use bare `setInterval`.
- **Errors** — show API failures through `describeError()` (`lib/errors.ts`), never raw axios messages.
- **Historical filters** — `getExecutionHistory(..., filter)` takes a `HistoryFilter` (`statuses`, `since`) and sends it as a Control Room list filter (`{operator: 'and'|'or', operands}` / `{operator: 'eq'|'ge', field, value}`), so totals and pages are server-side. Chip options live in `components/HistoryFilters.tsx`. Statuses seen in real data: `COMPLETED`, `RUN_FAILED`, `DEPLOY_FAILED`, `RUN_ABORTED` (plus `UPDATE` while running); map any new one in `HistoryCard`'s `STATUS` and the filter options.
- **Android back button** — `navigation/backHandler.ts` replaces RN's `BackHandler`: `useBackHandler(handler, enabled)` pushes onto a stack (latest first); `installBackButton()` wires `@capacitor/app`'s `backButton` and falls back to "press back again to exit". Open `Modal`s register themselves, so back closes the top modal.
- **Design system (Control Room style)** — tokens in `@theme` in `src/index.css`: `nav`/`nav-soft` (graphite from the AA logo, for header and nav pane), `page`, `surface`, `ink`/`ink-soft`/`muted`, `line`, `brand` (AA orange `#f05d28`, accents) and `brand-strong` (`#c4460f`, the primary button: white text passes AA contrast), `brand-tint`, and status colors `ok`/`fail`/`run`/`warn`. `.brand-line` is the logo's orange gradient, used as a thin accent under bars and on the active nav item. Font: IBM Plex Sans via `@fontsource`. Lists are a `Panel` (bordered table-like container with a header row); run/connection states use `StatusBadge` with Control Room labels (Completed, Run failed, Run aborted, In progress, Connected, Disconnected). Touch targets ≥ 44 px (`min-h-11`). The UX audit behind these choices is `docs/auditoria-ux.md`.
- **Dark mode** — same token names, redefined in `src/index.css` under `@media (prefers-color-scheme: dark) :root:not([data-theme="light"])` and `:root[data-theme="dark"]`, so components never branch on the theme. Never hard-code colors (`bg-white`, hex, `bg-ink/50` overlays): use tokens, including `on-accent` (text on brand/fail fills: white in light, near-black in dark), `backdrop`, `skeleton`, `lamp-idle`, `folder`; inline colors use `var(--color-*)`. `lib/theme.ts` holds the System/Light/Dark preference (localStorage `theme`, switcher at the foot of the drawer), sets `data-theme`, `theme-color` and the Android system-bar icon styles; an inline script in `index.html` applies it before first paint. The header and drawer stay graphite in both themes. On WebViews older than 140 (e.g. the emulator's 124) Capacitor insets the page and paints the bar strips in the phone's theme, so they don't follow an in-app override; setting the native window background doesn't change them (tried).
- **UI primitives** — `components/ui.tsx`: `Modal` is a native `<dialog>` opened with `showModal()` (variants `sheet` = bottom sheet, `center`, `page`); React controls visibility and `cancel`/`close`/light-dismiss route through `onRequestClose` (`dismissible={false}` blocks them). Mark the initial control with `data-autofocus`, not `autoFocus` (React's focus runs before `showModal()`). Don't lock body scroll or add `role="dialog"`/focus traps. `Switch` is `<input type="checkbox" switch>`; `main.tsx` loads the polyfill vendored in `public/vendor/input-switch-polyfill/` with a script tag (Vite won't `import()` from `public/`). Also `Sheet`, `Panel`, `StatusBadge`, `SkeletonRows` (list loading), `Lamp`, `ProgressBar`, `RefreshButton`, `LoadingState`, `ErrorState`, `buttonStyles`.
- **Motion** — GSAP via `src/lib/motion.ts` (registers `useGSAP`; wrap every duration/offset in `motionDuration()` so reduced motion drops movement). Used for dialog enter/exit, the drawer, progress bars, the launching gears and `useListEntrance` (row stagger once per data set/folder/page, not per poll). Don't reintroduce a global `animation-duration: 0.01ms` reduced-motion rule; handle it per animation. GSAP positions the drawer with `xPercent`, so don't add Tailwind `translate` classes there (they stack).
- `main.tsx` deliberately does not use `StrictMode`: its double-run effects fire duplicate logins (which invalidate tokens) and double polling.
